Every control takes its content from `values`, because `values` already carries the stored task on a first render and the reviewer's submitted text after a rejection -- which is what brings the form back filled in, with only the offending field flagged. The action is always a POST rule of the endpoint this screen belongs to, built with `url_for(..., _method='POST')` rather than written as a path: the create endpoint serves both `POST /tasks` and the `GET|POST` path this form was rendered from, and the edit endpoint likewise pairs `POST /tasks/` with `GET|POST /tasks//edit`. Naming the endpoint and the method keeps the two paths in app/blueprints/tasks.py the single source of both URLs, so a route change cannot leave a dead `action` attribute here. Nothing in this file decides a rule. The five control names are exactly the keys app.validation.parse_task_form reads -- title, description, assignee_id, status and deadline -- and every message comes from the parser through the two macros in partials/_field_errors.html: `error_summary` above the form lists every problem at once, and `field_error(errors, 'title')` renders the one sentence beside that field, owning the `-error` id a control points at with `aria-describedby`. No message string is written here, and `errors` being empty is the only thing that keeps the aria wiring off a control. The three status options are the closed set of app/models.py in the schema's order, their text coming from the `status_label` filter so STATUS_LABELS stays the single source of the words. The assignee select's first option is the empty value labelled "Unassigned", and that empty value is how an assignment is cleared -- the parser reads it as `None` rather than as a missing member. The deadline is a plain date input round-tripping the stored `YYYY-MM-DD` text; no date is parsed or formatted here. `required` and `maxlength` are declared for semantics and for the browser's convenience, and `novalidate` on the form makes sure the application's own messages are what a reviewer sees: app.validation rules that those attributes are convenience only, never the control, so a submission that bypasses them -- an empty title, an over-long one -- must reach the parser and come back with its sentence beside the field rather than being stopped by a browser bubble. The form carries no hidden navigation field. A data-entry post names no target: the view redirects to the task it saved, so there is nothing for the request to choose between and no redirect target any submission could supply.
