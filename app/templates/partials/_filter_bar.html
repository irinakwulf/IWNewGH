{# The task list's filter bar: three filters and their two controls. Included by app/templates/tasks/list.html and by nothing else. It is included rather than extended because it emits one GET form and no surrounding page: the view keeps its own heading, toolbar and result line around it. Two context variables come from that view (app/blueprints/tasks.py::task_list): filters the values app.validation.parse_task_filters produced -- "status", "assignee" and "deadline", each None when that filter is not applied. It is a mapping, and Jinja reads keys through attribute access, which is why the three selects read filters.. Every access is guarded, so a render that arrives without it still fills all three selects with "All" instead of raising. members app.services.members.list_members, already ordered by name, so the Assignee options are rendered in the order given and never sorted here. The "Apply filters" button is the only thing that submits the form: no select submits itself when its value changes, and the application ships no script at all, so nothing on the page moves until that button is pressed and the filter stays operable from the keyboard. Every option value below is one app.validation.parse_task_filters accepts, and the empty value is the "All" option it reads as "not applied". A non-empty value outside those sets is answered with HTTP 400, so this form must never be able to produce one. No set is restated here: the Status options iterate TASK_STATUSES, the Deadline options iterate DEADLINE_FILTER_LABELS and the Assignee control's "Unassigned" option reads ASSIGNEE_UNASSIGNED, all globals app/__init__.py publishes, so a bucket or status added to a vocabulary becomes selectable here and one removed stops being offered. #}
